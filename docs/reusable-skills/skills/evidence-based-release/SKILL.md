# 按证据完成构建、部署与交付

## 输入与交付边界

从用户要求确定交付到哪一步：代码、构建物、发布仓库、指定环境部署或设备验收。检查工作区、版本、部署入口、签名类型、持久化数据与已授权动作。记录用户现有改动；备份恢复点要覆盖实际交付范围，Git提交不等于数据库备份。

## 执行流程

1. 建立版本对照：源代码提交/工作树、包版本、客户端版本、后端版本、数据库迁移、部署镜像。先查现状，不自动升级无关依赖或重新创建部署。
2. 按变更风险选择验证。通常先类型/静态检查、定向测试，再相关回归及生产构建；使用仓库现有统一入口。文档技能包等低风险交付不需要重跑整个产品付费链路。
3. 对真实构建物做独立检查：内部版本、平台/包标识、签名或签名缺失、hash和产物路径。文件名写release不是签名证据，构建成功也不是设备可用证据。
4. 发布前检查运行环境和恢复方案。对数据库等持久化存储采用平台适配的备份，并说明是否做过恢复验证。只存在备份文件不能宣称可恢复；仅Git标签不能保护未跟踪数据。
5. 在已授权的目标环境执行既有部署方式。比较新构建与实际运行实例标识，保留持久化卷，按迁移兼容性决定回滚方式。不能用Windows本机容器冒充目标Linux主机。
6. 对外入口验证应带时间、预期版本和真实结果。健康接口、配置存在、供应商验证、真实业务请求分开记录；AI应用需验证关键用户动作和后续步骤。没有授权/凭证/设备时保留未验收状态。
7. 设备交付检查安装、启动、输入/平台功能、重启恢复和弱网降级。浏览器预览、模拟器和物理设备分别标记。
8. 汇总源码与产物状态，保留必要证据文件。只在任务范围内提交/推送/发版，不捎带用户其他改动或敏感配置。清理本次临时进程，留下可复现验收入口。

## 检查清单

- [ ] 已记录开始工作区状态，交付未混入无关改动。
- [ ] 相关自动化通过，失败/未运行有具体原因。
- [ ] 构建物内部版本、签名类型、hash经独立检查。
- [ ] 目标运行版本与构建版本一致，迁移与回滚可解释。
- [ ] mock、上游、公网、模拟器、真机证据分开。
- [ ] 用户数据和secrets未被删除、输出或包含进包。
- [ ] 只对有证据的层级说“完成”，其余列出下一步。

## 输出格式

交付文件链接 + 变更用途 + 验证表（层级/环境/日期/结果/证据）+ 限制。避免将一串测试数量作为唯一验收结论。
原项目多次发布的证据差异见 [案例](references/case-study.md)；练习场景见 [evals](evals/evals.json)。
