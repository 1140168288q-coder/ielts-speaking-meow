# V1.8 研究与设计取舍记录

## 研究结论

### IELTS 官方资料与题库结构

- IELTS Speaking 官方结构为 Part 1（短问答）、Part 2（cue card，准备
  1 分钟、作答 1-2 分钟）、Part 3（与 Part 2 主题相关的双向讨论）。
  公开资料如 [British Council Speaking week](https://www.britishcouncil.in/sites/default/files/5-speaking_week.pdf)
  与 [Cathoven cue card bank](https://resources.cathoven.com/ielts-speaking/cue-card-bank)
  都显示：Part 3 必须与 Part 2 关联，不能把 P2/P3 当成孤立题库。
- 本项目内置题库因此以“P2 cue card + relatedPart3Ids + P3 part2QuestionId”
  建模，符合考试结构，也为以后按卡片完整练习留好数据基础。

### GitHub 上 RAG / Memory / AI Tutor 项目

- [DeepTutor](https://github.com/wangwan221-cell/DeepTutor)：强调知识库
  主动参与每轮对话，而不是静态存储。V1.8 的 tutorContext / learnerContext
  采用同样思路，但只做本地词汇检索，不引入 agent 运行时。
- [ai-vocab-agent](https://github.com/liyang-27/ai-vocab-agent)：用
  FAISS + Agentic RAG + SRS 做词汇记忆。V1.8 刻意不上向量库：题库与知识
  库只有几十到几百篇短文档，Part+主题词的词汇检索已足够，成本为零、
  完全离线。
- [Tutor MCP](https://raw.githubusercontent.com/ArnaudGuiovanna/tutor-mcp/main/README.md)：
  把学习状态作为 tutor 的持久化上下文。V1.8 的长期 Memory 直接从真实
  sessions/expressions 聚合，不新建第二份状态，避免“两处记忆不同步”。

### 社区用户痛点

- 语言学习用户普遍反馈 AI 反馈太长、像批改作业、不易立刻行动
  （见 [YAP 反馈讨论](https://dev.to/yap2learn/frustrated-with-static-feedback-see-how-yap-delivers-real-time-results-4458)、
  [HN 上 Issen 讨论](https://hn.svelte.dev/item/44387828)）。
- 纯 AI 生成内容若脱离用户真实水平会被认为“不像自己能说的话”
  （[Duolingo AI 反思文章](https://redeployed.tecla.io/p/duolingo-s-ai-misstep-a-warning-not-a-fluke)）。
- 结论：反馈 UI 只展开“最值得改的 2-3 点”，细节折叠；参考回答保持
  三个难度/风格但 tab 化；改进版保持用户原有水平，并优先复用用户自己
  说过的素材。

## 技术取舍

| 候选方案 | 决定 | 理由 |
|---|---|---|
| 向量数据库/embedding RAG | 不用 | 知识库小、离线可靠、零新增依赖与费用 |
| 服务端账号 + JWT | 不用 | 第一版只做本机身份与数据隔离，userId 预留云同步 |
| 独立 Memory 表 | 不建 | sessions/expressions 已是长期记忆，聚合层只读推导，不会不同步 |
| 重新设计训练 UI | 不改流程 | 核心闭环已稳定，只重构反馈展示与素材复用入口 |
| 应用内解析季度 PDF | 不做 | 换季是开发事件，dev-time 脚本即可，运行时包体更小 |

## 版权与数据边界

- 原题库 PDF 不进入 git（`.gitignore` 忽略 `*.pdf`）；仓库只提交解析后的
  题目文本与生成器，原始文件仍留在项目目录供下次解析。
- 教学知识库为自写原则转述，不复制机构教材段落；不含任何官方评分描述
  或 band descriptor 原文。
- 第三方 API Key 仍只存在于 Backend 环境变量。
