# 公网 AI 服务分层诊断与整栈恢复

## 输入与保护范围

确认目标域名/入口、运行主机、服务依赖、持久化卷、当前部署方式及已有运维授权。保存版本、服务状态和脱敏日志。诊断优先只读；不要通过删除卷、重建数据库或全机关闭防护来“修复连接”。

## 执行流程

1. 明确现象的范围：本机应用响应、容器内响应、主机入口、公网入口、真实业务分别怎样。记录时间、版本和错误层级；HTTP错误码只是线索。
2. 检查执行引擎，再枚举全部必要依赖。引擎可用不代表数据库、业务服务和Tunnel都在运行；容器running也不代表应用ready。
3. 沿依赖顺序定位数据库就绪、迁移、应用健康、应用到上游。保存启动错误摘要；不要先调整模型参数去处理公网传输故障。
4. 单独检查Tunnel注册、边缘连接、DNS与出站路径。厂商控制API的HTTPS可达不代表隧道数据通道可达。使用该部署已配置且经核实的协议/端口，诊断失败后再考虑兼容传输。
5. 比较带代理与直连的实际路径、解析结果和路由影响。发现虚拟DNS/代理证据时缩小到对应路径；不要据此擅自切换VPN、改全局DNS或关闭安全软件。
6. 使用现有部署编排恢复缺失的完整依赖集合，保留数据卷。只有依赖健康、故障定位在Tunnel时才重启Tunnel。按故障类别限次重试，设置退避/冷却与日志；不健康的数据库不会被无限重启隧道修好。
7. 检查守护进程自身：父控制台退出、服务账号/交互登录限制、默认运行时限、电源策略、重复实例、日志位置。任务存在不等于当前运行，也不等于重启后必然自启。
8. 恢复后逐层复核服务就绪、Tunnel注册、公网无缓存探测和预期版本。公网健康接口200只证明对应接口成功；涉及AI/账号时需要独立业务探针。
9. 故障注入只在允许停机的测试环境或已有明确授权的窗口执行；否则交付可复现演练步骤。若可执行，停止一个已知服务并观察整栈恢复、数据保留及多次公网结果，最后清理临时进程。

## 检查清单

- [ ] 引擎、所有关键服务、应用ready、Tunnel、公网分别留证。
- [ ] 控制面和数据面连接没有混为一谈。
- [ ] 当前源码、镜像、容器与公网版本一致性已核对。
- [ ] 恢复动作不删除卷、不输出env全文和tokens。
- [ ] 监控有退避/冷却，生命周期符合运行环境。
- [ ] 演练是否实际执行、是否有业务请求、是否受网络条件限制均说明。

## 输出格式

给“分层状态 → 首个失败点 → 已做动作 → 恢复证据 → 环境限制/下一步”。证据不足时明确到哪一层，避免只写“已上线”。
实现案例及特定环境参数见 [案例](references/case-study.md)；迁移场景见 [evals](evals/evals.json)。
