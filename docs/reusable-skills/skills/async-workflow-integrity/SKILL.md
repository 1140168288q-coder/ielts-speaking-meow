# 保护多阶段 AI 流程的异步状态与用户输入

## 输入

找到一个可复现的交错事件：哪个操作先开始、用户期间修改了什么、哪个结果晚到、最终哪些字段错误。收集会话/实体标识、用户身份、修订号、存储事务接口和页面状态。

## 执行流程

1. 先列阶段与允许转换，包括等待、失败、取消和恢复。不同业务阶段保持独立任务身份与结果；共享单个 in-flight 标记之前证明不会吞掉合法操作。
2. 为请求绑定 owner、实体、操作类型和输入版本。捕获输入快照或单调修订号；文本相同但版本不同也可能属于新操作。服务返回后，在实际写入时再次核对身份和版本。
3. 旧结果过期时丢弃其副作用，保留新输入；必要时明确提示重新生成。仅在响应回调开始时检查、随后无条件写入，仍存在竞态。
4. 依赖前一阶段时显式排队；无依赖时可独立执行。等待期间给可见状态，避免悄悄 return。前序失败后是否继续由业务条件决定，不能永久卡住后序。
5. 使用事务、compare-and-swap 或受控串行更新完成 read-modify-write。锁的作用域应匹配实体和部署范围；单进程队列不能保证多进程安全。区分单记录原子性、跨表事务、跨服务操作。
6. 把服务端建议、编辑草稿、选中项分开管理。按新结果的身份初始化一次；用户编辑后无关 rerender 不得重置。确认前再次核对候选来源、当前输入版本与 owner。
7. 对可重复确认的写入设计业务去重键或唯一约束。需要跨实体一起完成时用事务；若无法做到，设计可恢复的分步状态和补偿，不能把“最后一步原子更新”当作整个流程原子化。
8. 在离开、重启、断网后恢复已保存输入。禁用按钮只能表达状态，不能替代写入端校验。对长等待提供退出或保留草稿路径，遵循目标产品交互约定。

## 检查清单

- [ ] 延迟A请求、修改成B、让A晚到，B及其成果仍保留。
- [ ] 交错保存多个字段，不出现整对象旧快照覆盖。
- [ ] 后续阶段等待可见，成功和失败后都能进入合法状态。
- [ ] 重复提交、重复点击确认不会重复积累同一成果。
- [ ] 分析到达后草稿正确初始化，用户编辑不被重渲染清空。
- [ ] 账号切换、实体切换、重启和失败不串数据。
- [ ] 报告明确事务实际覆盖哪些写入。

## 输出格式

给出事件序列、状态转换表、写入条件、最小修复与确定性时序测试结果。测试用可控制 resolve/reject 的任务模拟顺序，避免靠真实网络等待碰运气。
实现依据和不能夸大的原子性边界见 [案例](references/case-study.md)；跨项目场景见 [evals](evals/evals.json)。
