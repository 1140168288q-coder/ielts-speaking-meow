# 多 worker 计量、崩溃和重放设计

这是场景推演与待执行方案，未运行 API、访问供应商或验证线上结果。供应商既无幂等键也不能查询历史，在调用成功与本地落盘之间存在不可消除的不确定窗口，无法保证上游恰好执行一次。用户失败不扣额度也不代表供应商没有收费，这部分损失需由产品策略承担。

将“鉴权通过立即扣费”改为持久化预约额度。共享数据库保存操作记录、结果和计量账本，以账号加操作键建立唯一约束，并保存请求内容指纹。指纹覆盖图片内容以及影响结果的参数，不能只用图片 URL；可以使用服务端带密钥摘要，避免公开可比对的图片哈希。同账号同键同内容复用原操作，同键不同内容直接返回冲突；不同账号的操作完全隔离。

在同一数据库事务内完成创建操作、条件检查剩余额度和预约，避免三个 worker 同时透支。账本为每种额度变动设置唯一约束；重试请求不能再次预约或扣费。状态可用“已预约、待执行、执行中、已成功、已失败、结果未知”。进程 mutex 仅用于局部优化，共享事务、唯一约束和条件状态更新才提供跨进程协调。

worker 通过数据库原子抢占任务，使用租约及递增执行版本阻止旧 worker 覆盖新状态。但租约不能阻止已发出的供应商请求；执行中超时或租约到期后不能简单重新调用。需要区分明确尚未发送的任务和已经发送、可能发送的任务，后者按结果未知处理。客户端超时只结束等待，不自动取消已经执行的操作；原键重试查询持久状态，处理中返回可继续查询的状态。

成功后在一个事务中写入持久结果、UsageEvent、操作成功状态，并把预约转为实际扣费。失败则释放预约。若结果存对象存储，先写入不可变对象，再事务保存指针，另行清理无引用对象，不能把进程缓存当结果本体。

事故 A：供应商成功但事务前崩溃，本地无法判断其是否完成。操作进入结果未知，禁止后台无条件重发；向用户解释结果无法恢复，按期限释放预约且不扣本次额度。若用户选择重新生成，应明确这会发起新的供应商调用，创建新操作键；原操作保留终态，不再次收费。

事故 B：采用上述原子事务后，事件和结果一起持久化，重启直接读库返回，不调用供应商、不再次扣费。对于历史上已记账但结果丢失的数据，标为异常并进行唯一的补偿退款，不伪造成功或自动重跑。

图片和描述属于用户私有资料：按账号授权每次状态/结果读取，加密存储，日志只留操作号和脱敏错误，不记录图片、访问令牌或签名链接。定义结果、原图与账本各自保留期；删除内容后保留最小去重墓碑，原键返回结果已删除，不暗中重算。

验收应覆盖三个 worker 同键并发、不同键抢最后额度、同键换图、超时重试、调用前后及事务前后崩溃、租约过期、跨账号读取、删除后重放。分别检查供应商调用次数、用户净扣额、预约释放和结果可恢复性；不能把账本一次扣费误称为上游一次执行。
