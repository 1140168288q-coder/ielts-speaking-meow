# 把真实 AI 项目做成可信演示与项目材料

## 输入

确认受众、阅读/讲述方式、时长或页数约束、提交要求、可运行产品、已有截图与代码证据。若任务依赖比赛或平台当前规则，查核提供的原文和适用日期；不要把旧项目的规则当当前要求。

## 执行流程

1. 先跑通或检查一个完整用户任务：输入、AI帮助、用户行动、确认、可保存成果、再次打开/复用。选最能证明价值的一条链路，不靠功能数量堆砌。
2. 建立主张清单。每条标明“源码存在、历史自动化、当次真实运行、演示样例、规划或推断”，附环境、版本、时间和证据位置。测试数证明工程覆盖的一部分，不证明学习效果、营收或用户规模。
3. 分清模型行为与应用行为。固定流程编排、应用调用检索/TTS不等于模型自主选择工具；本地关键词检索不等于向量库；使用Memory不等于训练专属模型。用实际机制解释能力。
4. 从一条案例组织脚本，展示用户自己完成的动作和可持久化成果。AI示例标可替换；不能复制模型答案冒充用户进步。效果主张需要实际评估数据。
5. 使用独立、显著标记的虚构演示身份；数据通过产品既有导入/恢复能力进入隔离范围。先检查owner与恢复语义，避免污染真实账号。包含测试反馈时标明模拟AI，不能据此证明真实服务。
6. 采集真实界面并保存原图，记录设备/浏览器、尺寸、代码版本、数据性质、AI是否真实。裁切和遮盖隐私另存；不能改写结果或隐藏关键失败来制造成功证据。
7. 按媒介分别编辑：说明书能独立读懂，幻灯片服务现场讲述，视频围绕动作与转场。共享事实和素材，不直接把文档页面缩成幻灯片。用户未要某种格式时不额外制作。
8. 让界面与讲解用用户语言，技术细节仅在帮助理解或回答质询时展开。友好文案不能掩盖失败、等待和下一步。
9. 最终按成品尺寸检查可读性、截图与叙事一致、隐私遮盖和证据链接；实录不具备条件时交付明确待补的脚本/草稿。

## 检查清单

- [ ] 核心价值通过一个完整任务与保存成果展示。
- [ ] 模型自治、检索、Memory、效果主张与证据匹配。
- [ ] 实机、Web预览、mock与虚构演示数据清晰区分。
- [ ] 演示账号隔离，恢复/导入不覆盖真实资料。
- [ ] 每个关键截图可追溯到原图、环境与版本。
- [ ] 各媒介符合自身阅读方式，成品尺寸可读。
- [ ] 未验证功能、团队信息和指标没有被补写成事实。

## 输出格式

交付事实清单、贯穿案例、分镜/页序、素材清单及缺失证据；若已制作成品，再交付成品和实际QA结果。
案例中的媒介分工和演示数据边界见 [案例](references/case-study.md)；可迁移试用见 [evals](evals/evals.json)。
