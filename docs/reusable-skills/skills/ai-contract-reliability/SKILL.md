# AI 结构化输出与真实请求排障

## 输入与起点

收集失败操作、一次脱敏请求轨迹、客户端和服务端契约、Provider 适配层、健康状态及最近部署版本。先检查真实调用链，再决定是否修改提示词。没有轨迹时增加阶段级观测，不记录正文、凭证或完整响应。

## 执行流程

1. 按“用户操作 → 页面状态 → Provider 方法 → 请求发出 → 网关 → 上游 → 完成标志 → JSON → 字段 → 业务/来源规则 → 持久化 → 页面呈现”定位第一个失败阶段。
   - 请求根本没发出：查实例方法绑定、提前返回、共享忙碌锁。
   - HTTP 成功但回退：查截断标志、空内容、JSON、字段路径和来源校验。
   - 本机通过线上失败：核对部署版本和实际入口；不要继续修改已经正确的代码。
2. 写清结果契约及允许的失败结果。分别在服务边界与客户端入口做运行时校验；提示词不是校验器。根据业务风险选择未知字段策略，业务禁止项仍需显式验证。
3. 只为业务明确等价的表示做窄范围归一化。先列允许映射，再列必须拒绝的值。不要补造缺失事实、吞掉所有未知字段或把不认识的枚举改成默认成功。
4. 使用一个请求总时限覆盖尝试和退避。对齐上游、后端、客户端、代理的有效预算；同步请求通常给客户端留出后端处理之外的余量，但数值应来自目标链路。若网关更短，减小处理预算或改为异步任务。
5. 按错误类别决定重试。瞬时网络错误、部分限流/服务端错误可有限重试；权限、配置、无效输入和已确定的业务拒绝应给可操作提示。明确各层重试次数，避免层层相乘；重试可能产生重复副作用时先建立幂等语义。
6. 将“已配置、可达、上次上游验证、最近业务请求结果”分开。带时间与失败阶段更新健康信息；一次历史验证不能永久覆盖新的失败。诊断信息留在适当的详情入口，主界面说明用户能做什么。
7. 建立复现测试，再修复最小故障点。使用真实 Provider 实例和可控 transport 覆盖调用绑定、解析、错误映射；用纯函数 mock 只能证明页面接线的一部分。
8. 依次验证：定向用例、相关回归、目标部署版本、真实业务请求。真实请求仅在已有授权、可用凭证与成本边界内执行，使用合成内容；否则明确缺哪一层证据，不能把 mock 当作上线成功。

## 检查清单

- [ ] 失败阶段和字段路径有证据，不凭“看起来像密钥问题”定位。
- [ ] 已覆盖合法输出、等价格式、非法枚举、截断、缺失字段与业务拒绝。
- [ ] 超时、重试和最终失败均保留用户输入与已有成果。
- [ ] 状态反映最近请求；观测不包含私人正文或凭证。
- [ ] 页面到真实 Provider 的链路被测试，关键后续步骤也被覆盖。
- [ ] 分开记录 mock、真实上游、目标公网、设备端的验证状态。

## 输出格式

交付“症状与根因 → 最小变更 → 契约映射/拒绝规则 → 验证矩阵 → 未验证范围”。若未改代码，交付同样结构的可复现诊断和下一步。
需要理解本技能依据及项目特例时，阅读 [案例](references/case-study.md)。迁移试用场景见 [evals](evals/evals.json)。
