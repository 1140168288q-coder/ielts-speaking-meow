# 案例：口语练习应用如何区分参考内容与用户事实

## 历史演进

项目由单次反馈扩展到两次作答、本地教学 RAG、个人表达复用和长期 Memory。
之后加入个人知识库导入、自然提升版难度设置、来源展示与账号同步。
这一扩展带来关键问题：导入文档和 AI 示例里也有第一人称经历，不能因为它们能帮助生成答案，就认定为用户真实经历。
产品因此把简单优化与扩展生成分开，并在第二次回答后独立确认 Memory 候选。
历史需求和完成范围分别见 `docs/AI_DIFFICULTY_USER_RAG_QUESTION_MANAGEMENT_PLAN.md:30`、`:68`、`:248`，以及 `docs/AI_DIFFICULTY_USER_RAG_QUESTION_MANAGEMENT_RESULT.md:13`。
这些是原项目溯源标记，复制本技能到其他项目后不需要访问原仓库。

## 失败教训与边界

- 合法来源 ID 不能证明输出结论正确。白名单阻止虚构来源，不完成语义蕴含证明。
- `src/application/practiceService.ts:627-639` 的英文 token 覆盖阈值为 0.75；它能拦截部分无根据来源，但可能漏过否定、词序改变、关系颠倒。不要写成“事实真实性已保证”。
- 用户确认是必要的产品控制，也可能出错。高风险应用应依据风险增加可审查证据和更严格复核。
- `src/application/practiceService.ts:338-340` 先逐条写语料，随后才原子更新练习记录。该流程不是横跨语料与 Memory 的全局事务；复制到强一致场景需要重新定义提交单元。
- 历史反馈中的内容不应该通过摘要再循环成为新用户事实。事实源和派生视图要分开。

## 不可照搬的参数与验证状态

原项目面向短篇英语口语练习，知识上下文最多 2400 字符、来源条目和候选数量也有限制；这些预算不是所有项目的最佳值。
Part、题目、语料等分类需替换成目标业务的任务、主题和事实类型。
案例是本次静态检查源码、测试定义和项目文档所得；本技能生成过程中没有重新执行上述业务测试或调用真实 AI。
最终交付应把“有测试定义”“测试已运行通过”“真实服务已验证”明确分开。
