# AI 重试、配额和幂等结算

## 输入

确认功能、计量单位、成功定义、认证身份、客户端重试规则、上游幂等支持、数据库约束、进程数和结果保留要求。区分用户额度与供应商账单：本应用不扣用户额度并不代表上游没有产生成本。

## 执行流程

1. 定义“可结算成功”：鉴权通过、上游执行成功、结果通过结构与业务校验。失败是否计量由明确产品规则决定；不要因为已经发送HTTP就默认交付成功。
2. 将授权检查、执行、结果校验和原子结算拆开。检查余额不等于保留名额，分析多个请求同时越过检查的情况。
3. 幂等域至少包含认证用户、业务功能/路由、稳定操作键。由实体+操作+修订或随机操作ID生成键，不把私人正文放入键。为规范化请求计算摘要用于检测同键异内容；摘要仍按敏感派生数据管理，不把哈希当匿名化。
4. 对同键同内容复用在途任务或可用结果；同键异内容拒绝；不同用户相同键彼此隔离。相同操作重试保留键，新输入或明确新操作换键。
5. 用数据库唯一约束和事务保障结算去重。若还需防止重复上游调用，必须在执行前有覆盖多worker的协调机制。单机mutex/内存缓存不足以承诺跨实例只执行一次。
6. 按规模选择协调方案。低并发可考虑持有数据库行锁覆盖执行，但说明长事务、连接占用及同用户阻塞；高并发优先评估持久化操作记录、额度预留/释放、带租约任务。不要直接把示例的锁策略变成通用架构。
7. 明确缓存过期、重启和执行结果不明的语义。已结算但响应不可恢复时返回明确状态；不要自动再调用并伪称“安全重放”。如果新键代表新付费操作，应告知调用方。
8. 对“上游已执行、本地提交前崩溃”单独设计恢复或标记不确定。没有上游幂等/查询协议时，不能保证端到端恰好一次；记录已实现的是结算去重还是执行去重。
9. 用可计数 fake provider 和目标数据库测试失败、重试、并发和重启。SQLite或单worker通过不证明生产锁语义；真实付费探针只在授权范围内最小执行。

## 检查清单

- [ ] 上游超时、非法JSON、业务拒绝的结算符合产品约定。
- [ ] 同键同内容：计量次数、上游次数、返回值分别验证。
- [ ] 同键异内容拒绝，跨用户隔离，新修订可执行。
- [ ] 并发靠最终数据库约束兜底，不只是先查后写。
- [ ] 余额耗尽后已有成功操作仍可按约定重放。
- [ ] 缓存失效、进程重启、提交前崩溃都有明确结果。
- [ ] 日志不包含凭证、完整请求和私人结果。

## 输出格式

交付操作身份规则、成功/失败计量表、并发协调方案、重放决策表、故障测试证据和无法保证的范围。
读取 [案例](references/case-study.md) 了解原项目的演进和长事务取舍；试用提示见 [evals](evals/evals.json)。
