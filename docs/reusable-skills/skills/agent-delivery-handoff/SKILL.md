# 可恢复、可交接的 AI 协作开发

## 输入与先行检查

读项目约束、现有实现、工作区状态、近期变更与用户已确认决定。找清源码、构建物、部署和持久化存储的位置；路径别名/链接可能指向同一目录。只问影响方案或无法从现状推断的问题，不重开已经确认的选择。

## 执行流程

1. 写清本轮问题、目标行为、不变约束和验收证据。将每项需求映射到受影响层：页面、用例、契约、数据、服务、发布；没有需求驱动不要扩大重构。
2. 建立可恢复点并保护已有工作。Git工作区清单、提交/标签、外部数据备份各有范围；不默认把用户改动提交，也不把标签当全部文件和数据库已备份。
3. 规划按风险依赖排序的小阶段：先数据/主链路问题，再体验和展示。每阶段说明输入、改动位置、完成条件、失败后的选择；不以“写完代码”作为所有阶段的共同终点。
4. 需要交接时输出自包含任务说明：准确目录/基线、已批准选择、待解决根因、具体范围、测试入口、部署权限和已知阻塞。接手者应能执行，不必重新猜原对话。
5. 执行中维护简短进度和证据。新发现改变根因或边界时更新方案；例行实现选择由执行者处理，不因文档里出现“确认”二字反复要求用户审批。
6. 工具失败时先区分产品故障与工具故障。相同方法连续失败两次可作为切换策略的信号：检查进程/端口/超时，缩小验证，使用一次性前台命令或可回收后台任务。不能把替代验证能力写得比原验证更强。
7. 测试选择围绕可观测结果：契约用例、真实适配层、持久化恢复、目标运行入口。mock通过不替代真实Provider接线；浏览器预览不替代原生平台能力。无法完成的一层记录原因和最小剩余步骤。
8. 收尾对照原目标审查差异、执行相关检查、清理临时进程、交付准确状态。只有请求包含部署/发布时才执行到对应外部动作；权限和阻塞不通过“先做了再说”绕过。

## 检查清单

- [ ] 开始时的用户工作、绝对路径和数据边界已查清。
- [ ] 已确认决策被继承，问题和范围足够具体。
- [ ] 每阶段有可观察完成条件和失败替代路径。
- [ ] 交接文件能独立理解，包含版本和权限范围。
- [ ] 卡住时换证据路径，不重复启动遗留进程。
- [ ] 最终明确代码/构建/部署/设备各层状态。

## 输出格式

短任务用简短计划和结果即可；复杂交接使用“基线 → 问题证据 → 已定选择 → 分阶段执行 → 验证与发布 → 限制”。不要把原项目每次都写长文档的做法套到一行修改。
原项目的交接、检查点和自救经验见 [案例](references/case-study.md)；试用场景见 [evals](evals/evals.json)。
