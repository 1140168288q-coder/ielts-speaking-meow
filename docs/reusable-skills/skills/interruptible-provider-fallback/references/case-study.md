# 案例：TTS 从“有备用”到真正可切换、可停止

证据读取于 2026-09-20。以下原项目路径仅供溯源，技能复制到其他项目后无需访问。

## 历史问题

V1.5 修复记录 `docs/V1.5_RELEASE.md:24-56` 显示：

- 之前配置状态不足以表达上游是否真正验证，修复后分开 configured 与 verification。
- 无后端时曾等云端 60 秒超时；改为健康未知立即系统播报，失败后短期熔断。
- 系统能力不足时可能显示“正在播报”却无声；增加引擎和英语语音包检测。
- 换音色后同文本会复用旧音频；缓存键扩展到声音、模型、语言、速率、音高和配置版本。

这些是具体故障修复记录，不是所有项目都应使用该超时值或健康策略的依据。

## 当前实现

- 可用性检查区分健康未知、未配置及上次验证失败：`src/infrastructure/backend/backendTtsProvider.ts:59-72`。
- 缓存键字段：同文件第 79-88 行；云端失败熔断：第 96-118 行；缓存写失败不阻断结果：第 120-126 行。
- 多个异步边界检查 generation，stop 递增令牌阻止晚到结果播放：同文件第 74-145 行。该机制不表示后台 HTTP 已真正取消，仍可能消耗上游资源。
- 主备切换前停旧执行者，并检查操作是否有效：`src/infrastructure/speech/fallbackTtsProvider.ts:145-190`。
- 备用状态委托给活动 Provider：同文件第 193-206 行。
- 播放协调器只在短暂的独占步骤中停止旧声、设置活动声源，等待播放完成放在独占区外；结束时核对 activityToken：`src/infrastructure/speech/audioCoordinator.ts:73-135`。

这使“停止”有机会打断播放，且旧完成事件不能把新播放状态清空。可迁移到预览、生成结果展示等可重做操作，但不可直接用于扣款等不可逆请求。

## 不宜照搬

60 秒超时和熔断、英语语音包检查、固定 TTS 供应商及特定音色均是原项目参数。根据目标操作的预算、用户耐心和备用质量重新选择。
健康未知就降级适合已有可用系统 TTS 的场景；没有等价备用或结果风险高时应展示等待/无法完成，而不能虚构结果。
默认可用性不要求实时健康探针逐次请求；需在新鲜度、成本和实际操作失败间作适当取舍。
