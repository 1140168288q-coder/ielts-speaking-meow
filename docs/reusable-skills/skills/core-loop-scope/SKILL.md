# 从价值闭环决定功能范围

把用户要完成的任务转成可验收的闭环，再决定保留、替换、推迟和退役的能力。
避免把某个项目的技术选型或禁用项当成所有 AI 应用的规则。

## 输入

- 用户目标、主要使用者、目标设备和实际使用环境。
- 当前入口、用户输入、系统处理、用户下一步、结果保存的已有实现。
- 已承诺功能、明确非目标、数据兼容要求和授权范围。
- 已有代码、测试、发布记录；若有历史争议，提供相关版本提交。
- 本次交付类型：分析方案、实现变更、发布验收，允许组合。

信息不足时先检查现有材料；只询问会改变产品边界的缺失决策。
用户已经明确的约束不重复确认。分析任务不自动升级成代码或部署任务。

## 执行流程

### 1. 建立当前事实

阅读当前约束和主流程实现，确认数据落点、外部依赖和真实失败路径。
将发现标为以下四类，避免混写：

- 用户目标或明确产品决定。
- 文档中的设计与计划。
- 当前源码已实现行为。
- 指定版本曾经完成的验证及尚未验证项。

回顾历史时，版本发布记录可能被后来编辑；用对应提交快照交叉核对。
没有动机记录时只描述发生了什么，不能把工程推断写成用户当年的理由。

### 2. 写出最短完整闭环

用具体动作串起：触发 → 用户投入 → 系统帮助 → 用户下一步 → 持久结果。
说明结果对用户有什么用；“模型成功生成”通常只是中间事件。
学习类应用可能以用户再次尝试为结果，工具类应用可能以用户确认并应用结果为终点。
不得强制所有 AI 应用都采用双答、评分禁令或固定的反馈数量。
为每个步骤写出必要输入、完成标志、失败后的可继续路径。

### 3. 将功能映射到闭环

对每项拟做功能说明它修复哪个断点、减少什么成本、如何验证。
分为必须、可选增强、以后再做、明确排除；只使用本项目有依据的分类。
先修复使用户不能完成任务或会丢数据的断点，再考虑增加功能。
若简化方案可以利用操作系统或成熟服务已有能力，比较体验、隐私、成本和支持范围。
可替代不等于应删除：没有行为变更授权时先提交建议，不直接退役功能。

### 4. 对能力退役建立完整清单

已有明确授权时，追踪待退役能力覆盖的各层：

1. 页面入口、状态、提示和帮助文档。
2. 应用服务、接口、调用链和后台任务。
3. 服务端路由、供应商配置、环境变量和依赖。
4. 设备权限、构建配置和运维探针。
5. 新数据写入方式、旧数据读取、备份恢复和历史展示。

区分“停止创建新数据”和“删除历史数据”；后者需要独立的数据生命周期依据。
保留必要的历史读取适配，但阻止旧入口在新流程重新出现。
替代流程应先具备可用入口，再关闭旧路径；保持已有用户能完成原目标。

### 5. 建立行为级验收

围绕用户完成闭环，而不是围绕页面数量验收。
覆盖正常流程、依赖不可用、操作中断、重复操作、关闭重开和升级后读取。
优先使用现有测试工具；涉及设备能力时另标真机证据，不能用模拟测试代替。
旧行为已获授权退役时，删除过时测试并加入防回归断言，而非保留无效功能来满足旧测试。
工程门禁通过与真实用户流程完成分别报告。

### 6. 决策和交付对齐

为范围变更记录：原行为、新行为、依据、数据兼容、验证、剩余限制。
实现完成但未发布时明确标记；历史曾验证不能代替当前发布验证。
若核心目标尚未实现，指出具体断点和下一步，不用新增功能掩盖未完成。

## 检查清单

- [ ] 闭环终点是可观察的用户结果，且每个保留功能有明确作用。
- [ ] 范围决定来自当前用户目标；推断、计划、实现和验收已区分。
- [ ] 退役覆盖所有入口与依赖，同时保留需要的历史数据读取和恢复能力。
- [ ] 外部能力不可用时，约定的基础流程仍可完成且用户输入保留。
- [ ] 正常、失败、中断、重启或迁移均有与本次变更相称的证据及限制说明。

## 输出格式

交付一份与任务规模相称的记录：

1. **核心闭环**：一条动作链和最终成功条件。
2. **范围决定**：功能、支持的闭环步骤、保留/变更决定及依据。
3. **迁移影响**：入口与依赖变化、旧数据处理、必要回滚边界。
4. **验收结果**：实际运行内容、结果、未验证设备或服务。
5. **待决事项**：仅列阻碍当前目标的缺失信息。

本技能不要求指定技术栈、目录层级、应用平台或 AI 供应商。
需要理解本技能由哪些成功做法和返工形成时，阅读 [项目案例](references/case-study.md)。
案例的原项目路径仅用于溯源，复制技能后无需访问该项目。
